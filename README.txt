teachers self-bootstrap ভালনারেবিলিটি — ফিক্স
===========================================================================

⚠️ যা পাওয়া গেছে (আগেরটার চেয়েও বেশি ঝুঁকিপূর্ণ):
---------------------------------
teachers কালেকশনের create rule-এ একটা পুরনো শাখা ছিল, মাল্টি-টেন্যান্ট
ফিচার আসার আগের সময়ের জন্য বানানো — যাতে কোনো পুরনো শিক্ষক প্রথমবার
লগইন করলে নিজে নিজে নিজের teacher ডকুমেন্ট বানিয়ে নিতে পারে:

  (request.auth.uid == uid &&
    request.resource.data.get('isAdmin', false) == false &&
    request.resource.data.get('active', true) == true)

সমস্যা: এখানে madrasaId কী হবে তার ওপর কোনো শর্তই ছিল না। মানে —

  ১. যে কেউ একটা নতুন Firebase ইমেইল/পাসওয়ার্ড অ্যাকাউন্ট বানায়
  ২. তারপর সরাসরি teachers/{তার-নিজের-uid} ডকুমেন্টে
     madrasaId: "<আপনার আসল মাদ্রাসার id বা যেকোনো ভবিষ্যৎ গ্রাহকের id>"
     লিখে দেয়
  ৩. সাথে সাথে সে সেই মাদ্রাসার একজন (non-admin) শিক্ষক হয়ে যায় —
     সব শিক্ষার্থী দেখা/এডিট/মোছা, রেজাল্ট, ফি, অ্যাটেনডেন্স, এমনকি
     শিক্ষার্থীর PIN রিসেট করার পূর্ণ ক্ষমতাসহ

এটা আগের "madrasa-001"-নির্দিষ্ট সমস্যার চেয়ে বড়, কারণ এটা **যেকোনো**
মাদ্রাসার (আপনার নিজেরটা এবং ভবিষ্যতের সব গ্রাহকেরটা) জন্য কাজ করতো।

✅ যা ঠিক করা হয়েছে:
---------------------------------
এই শাখাটা সম্পূর্ণ মুছে ফেলা হয়েছে। যাচাই করে দেখা হয়েছে এটা মোছার পরও
কোনো বৈধ ব্যবহার ভেঙে পড়বে না, কারণ:
  - আপনার নিজের অ্যাকাউন্টের teacher doc আগে থেকেই তৈরি আছে (স্ক্রিনশটে
    email/isAdmin/madrasaId/createdAt সহ কনফার্ম করা হয়েছে)
  - সেলফ-সাইনআপ নিজেই isAdmin:true সহ আলাদা, সুরক্ষিত শাখা দিয়ে
    ডকুমেন্ট বানায় (madrasa-001 ব্লক করা, ইতিমধ্যে ফিক্স করা)
  - অ্যাডমিন যখন "শিক্ষকগণ" স্ক্রিন থেকে নতুন শিক্ষক যোগ করেন, সেই
    ডকুমেন্টও অ্যাডমিন নিজেই বানিয়ে দেন (isRequesterAdmin() শাখা দিয়ে)

কোনো app.js পরিবর্তন লাগেনি।

📋 করণীয়:
---------------------------------
এই firestore.rules Firebase Console-এ Publish করুন।

Publish করার পর নিজে টেস্ট করে দেখতে পারেন: আপনার নিজের অ্যাকাউন্ট দিয়ে
স্বাভাবিকভাবে লগইন করে সব ফিচার (শিক্ষার্থী তালিকা, উপস্থিতি, রেজাল্ট
ইত্যাদি) আগের মতোই কাজ করছে কিনা।
